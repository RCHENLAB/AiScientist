The hint said "pass the label column as groupby". The question had already taken groupby. The advice became unsatisfiable, nothing mentioned stratify_by, and the model dropped it entirely.

模型 · 一次性生成model · one-shot generation

PI 把"用户要的第 3 步"和"skill 要的第 5 步"拼在一份计划里,没注意到第 5 步的措辞("instead of treating cells as independent replicates")等于宣告第 3 步无效。

The PI concatenated the question's step 3 and the skill's step 5 into one plan, without noticing that step 5's own wording ("instead of treating cells as independent replicates") declares step 3 invalid.

脚手架 · 没有第二双眼睛scaffolding · no second pass

_plan_review 的检查清单正好覆盖这一条,但 step_meetings 默认 False,gateway 从不设置它。计划直接进入执行。

_plan_review's checklist covers exactly this, but step_meetings defaults to False and the gateway never sets it. The plan went straight to execution.

脚手架 · 工具守卫已被删除scaffolding · the tool guard was gone

当时 HPC3 上那版 run_de 还有条件列守卫,拦了 5 次,模型用 force=true 绕过 3 次。当前 main 和 prod 里这个守卫已经不存在了 —— 今天再跑一次,不会有任何东西拦住它。

The run_de staged on HPC3 that day still had the guard: it refused five times and the model bypassed it three times with force=true. That guard is absent from current main and prod — the same run today would not be stopped at all.

脚手架 · Critic 判错了对象scaffolding · the Critic judged the wrong thing

第 5 步(pseudobulk)实际调的是第三次 run_de(force=true),Critic 给了 ACCEPT 0.95 —— 它判的是"有没有产出证据",不判"证据是不是这一步声称的方法产的"。

Step 5 (pseudobulk) actually issued a third run_de(force=true), and the Critic returned ACCEPT 0.95 — it judges whether evidence was produced, not whether the evidence came from the method the step claimed.

怎么解读这份成绩单How to read that scorecard

这些失败分成三类,只有第三类是"模型不够好":

The failures fall into three classes, and only the third is "the model is not good enough":

  1. 任何模型在一次前向生成里都做不可靠的事 —— 回读并自检自己刚写的长输出。这是架构问题,解法是第二次带审查角色的调用,不是更大的模型。
  2. Things no model does reliably in one forward pass — re-reading and self-checking its own long output. Architectural; the fix is a second call in a reviewing role, not a bigger model.
  3. 输入本身就是错的 —— "per donor" 那一步是 profile 承诺了一个不存在的 donor 列。换任何模型都会这么规划。
  4. The input was wrong — the "per donor" step followed a profile that promised a donor column which does not exist. Any model would plan the same thing.
  5. 真正的指令遵循瑕疵 —— 无视 majorclass、在已 QC 的数据上重做 QC。这里确实有余量:更强的模型大概率能接住。但正确的杠杆是把指令放进可执行的槽位(告诉它 stratify_by),而不是指望它在一个已被占用的槽位上想办法。
  6. Genuine instruction-following lapses — ignoring majorclass, re-running QC on QC'd data. There is real headroom here and a stronger model would likely have caught them. But the right lever is putting the instruction in an actionable slot (telling it about stratify_by), not hoping it improvises around one already taken.

这个判断的强度How strong this claim is

n = 1。我看的是一次运行,不能据此对模型下统计结论。要真回答"能不能胜任",需要固定同一份数据和同一个问题,在修复前后各跑 N 次,记录:(a) 计划里是否出现自相矛盾的步骤对;(b) 是否复用了已有标签;(c) 是否规划了数据不支持的步骤;(d) 计划复核是否捕获。这个实验很便宜(GPU 是免费的 gpu32),而且它同时能量化修复的效果和模型的余量——是决定要不要上多层模型路由的唯一依据。

n = 1. This is one run; it cannot support a statistical claim about the model. Answering "can it do the job" properly means fixing the dataset and the question, running N times before and after the fixes, and recording: (a) whether the plan contains a self-contradicting pair of steps; (b) whether existing labels were reused; (c) whether a step the data cannot support was planned; (d) whether the plan review caught it. The experiment is cheap — the GPU is the free gpu32 pool — and it would quantify both the fixes' effect and the model's headroom, which is the only sound basis for deciding whether to adopt multi-tier model routing.

The first version of the plan review cut plans from a mean of 4.6 steps to 1.9.
